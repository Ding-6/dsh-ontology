# 本体开发指南

这份指南讲清楚一件事：**这个插件在你自己的本体平台上开发本体应用时，怎么当副驾用。**

插件不连接你的平台，也不替你写平台代码。它做四件事：

1. 把业务**分析**成可建模的东西（参与者、对象、关系、规则、边界、验收口径）；
2. 维护一份**统一语义层**——所有专家（agent）看到同一份上下文，AI 生成约 80%，专家校准约 20%；
3. 把语义层翻译成**能落地的代码方案**（数据模型、规则引擎、API 契约、前端设计、本体驱动、测试方案）；
4. 记住你的**平台操作手册**，你要它教你操作时，它照手册说。

---

## 一、先认识面板

侧栏点「本体建模工作空间」进去，九个页签：

| 页签 | 干什么 |
| --- | --- |
| 工作台 | 今天该做什么、谁在忙、哪些逾期 / 阻塞 |
| 看板 | 八列：场景筛选 → 语义设计 → 待生成 → 建模中 → 专家校准 → 一致性校验 → 场景验收 → 已发布 |
| **语义层** | 本体的家：八类资产、多本体、建模建议、应用蓝图、领域骨架、操作手册、服务封装 |
| 场景 | 一条本体应用的业务场景：目标、范围、功能点、验收标准 |
| 校验 | 用例与执行记录（接口 / shell / 数据库三种执行器） |
| 本体版本 | 版本、灰度、发布门禁 |
| 项目 / 效能 / 设置 | 项目与迭代、周期与成本、集成配置 |

**语义层是核心**，其余页签是围绕它的工作流。

---

## 二、语义层：八类资产

不预置任何行业数据。资产分三层：

| 层 | 资产 | 关键字段 |
| --- | --- | --- |
| 数据层 | **业务对象** | 编码 / 业务域 / 属性（名 + 类型，必填标 `!`）；可选父类 |
| 数据层 | **对象关系** | 起点 / 关系名 / 终点 / 基数（1-1 / 1-N / N-1 / N-N） |
| 数据层 | **术语方案** | 概念：英文标识 / 显示名 / 定义 / 上下位词 / 相关词 |
| 数据层 | **对象实例** | 所属类 / 属性值 |
| 逻辑层 | **业务规则** | 类型（约束 / 派生 / 默认 / 计算 / 路由）/ 表达式 / 作用范围 / 依赖规则 / 表达式语言 |
| 逻辑层 | **校验形状** | 目标类 / 约束列表（路径 + 算子 + 取值 + 提示）/ 严重级别 |
| 行动层 | **可调用行动** | 类型（查询 / 写入 / 通知 / 工作流）/ 目标系统 / 入参 / 返回 / 前置条件 / 副作用 / 是否幂等 / 权限 |
| 行动层 | **应用场景** | 解决什么 / 参与者 / 输入 / 输出 / 关联资产 |

规则表达式支持五种语言，各有适用面：

| 语言 | 什么时候用 |
| --- | --- |
| `natural` 自然语言 | 业务方自己看得懂、要给人审的规则 |
| `shacl` | 约束要能自动校验数据（对齐 W3C SHACL） |
| `jsonlogic` | 前后端共用一份可执行的规则 |
| `sqlish` | 规则本质是查询 / 过滤条件 |
| `formula` | 计算型规则（派生、汇总） |

**每条资产都有状态**：`AI 草稿`（AI 生成的，等人确认）、`已确认`（专家校准过）、`已废弃`。
**废弃的资产不再算缺口**，但也不会消失——历史可追。

### 多本体并存

顶部可以新建、切换本体容器。做民用、商用、军用三套应用，就建三个容器，资产互不污染。
导出、服务封装、应用蓝图都只作用于**当前本体**。

---

## 三、四种角色，一条链

| 角色 | 在本体开发里干什么 |
| --- | --- |
| **业务**（本体业务专家） | 澄清场景：参与者是谁、涉及哪些对象、关系与规则、异常与边界、验收口径 |
| **架构**（本体架构师） | 设计语义模型：对象划分、关系与规则表达式（并说明选哪种表达式语言及理由）、行动与 API |
| **建模**（本体建模师） | 落地语义资产：把方案登记进语义层（AI 草稿），清掉建模建议器点名的缺口 |
| **校验**（本体校验师） | 验证：一致性校验用例 + 回归；测「本体 → 生成物 → 运行时」这条链没被绕过 |

规则：**AI 产出先落草稿，专家校准后才算数。** 每一步都在卡上留评论、交付物与提交记录。

---

## 四、建模建议器：先看机器的结论

语义层面板有「建模建议」区，也可以直接让 agent 调 `ontology_review_advice`。它给三类结论：

- **blocker**：对象没有任何属性（生成不出数据模型与接口）、行动没有目标系统（落不成接口）、规则没有表达式、关系指向不存在的对象……
- **warn**：对象没有编码、继承成环、规则依赖了一条不存在的规则、写操作没声明幂等或前置条件……
- **info**：AI 草稿还没人校准、术语没写显示名、应用场景没写参与者……

每条都带**可执行的修改点**，照着改即可。

## 五、应用蓝图：语义层 → 能写代码的方案

点「生成蓝图」，产出六章 Markdown：

1. **数据模型设计** —— 表、列、SQL 类型映射（`string→varchar(128)`、`money→numeric(18,2)`、`json→jsonb` …）、索引、外键与中间表；
2. **规则引擎设计** —— 规则分组、按依赖拓扑的求值顺序、冲突口径、TypeScript 的 `Rule` / `RuleContext` / `RuleResult` 骨架；
3. **后端与 API 契约** —— REST 路径表、OpenAPI 3.1 片段、错误码约定（400 / 404 / 409 / 422 / 500）、Repository 骨架；
4. **前端设计** —— 页面清单（列表 / 详情 / 关系图 / 规则页）、字段与组件、状态管理建议、前端 schema 骨架；
5. **本体怎么驱动应用** —— 七步流水线、目录约定（`ontology/` → `generated/` → `src/`）、三条护栏；
6. **测试方案** —— 可执行的 HTTP 用例矩阵（缺必填→422、详情查询、关系查询、行动执行、规则正反例）。

蓝图是**方案不是成品**：它照着你语义层里的字段、关系、规则生成，语义层改了就重新生成。

## 六、领域骨架模板：先有结构，再填业务

八套骨架，**只给结构，不含任何行业业务数据**：

`general` 通用业务 / `industrial` 工业与物联网 / `safety` 公共安全 / `health` 医疗健康 /
`defense` 国防与装备 / `geo` 地理空间 / `finance` 金融与风控 / `knowledge` 知识与文档。

点「生成骨架」会实例化成一批「AI 草稿」资产（对象 / 关系 / 规则 / 行动）。
它们的字段是通用的：标识、名称、状态、时间、责任人、编码、标签。你按自己的业务改字段、改规则、改关系，
再逐条校准。骨架的作用是**省掉从零想「一个领域通常有哪些对象」**，不是替你建模。

## 七、平台操作手册库：让它教你操作平台

**插件随包内置《智元·本体智能体平台操作手册 V2.0》（86 个章节）**，随插件一起分发，不用你再准备：

- 语义层面板的「平台操作手册库」顶部就是这本内置书（书名 / 版本 / 章节数）；
- 点「**载入到手册库**」把 86 篇灌进台账，之后 `ontology_guide_search` 检索命中来源标「已入库」；
- **不载入也能检索**——检索框同时搜「已入库」和「内置书」，所以随时可以问；
- 手册里没有的内容，agent 会明说手册里没有，而不是编平台步骤。

你自己的平台手册用「**存入手册**」（标题 / 来源 / 正文 / 标签）加进同一本库，两者在检索里一起排序。

> 手册类条目默认按「已确认」入库，不会占用「AI 草稿待校准」名额，语义层闸门不会被手册卡住。

### 内置手册覆盖了什么

| 手册章节 | 你可以在插件里问 |
| --- | --- |
| 2.5 本体工作台（新建 / 模型 / 发布 / 版本 / 权限 / 数据管道 / 对象浏览器） | 「平台上怎么新建本体」「对象类型的主键和标题键怎么配」「发布本体要走哪几步」「数据管道怎么抽数」 |
| 2.1 能力注册中心（适配器 / MCP 服务 / API 直连，OpenAPI / Swagger 导入） | 「平台怎么把一个接口注册成能力」 |
| 2.2 SKILL-工具（创建 / 工作流 / 编辑 / 上架 / 授权） | 「工具上架要过哪几项准入」「怎么只授权给某个用户组」 |
| 2.3 SKILL-技能（新建 / 导出 Skill.md / 导入） | 「技能怎么导出成 Skill.md 压缩包」 |
| 2.6 知识工作台（上传 / 解析 / 分片 / QA / 权限 / 召回测试） | 「文档上传有什么格式和大小限制」「召回阈值在哪调」 |
| 2.7 数据工作台（数据集 / 指标 / 维度 / 权限） | 「数据集怎么用 SQL 建」「指标口径写在哪」 |
| 2.8 领域服务 | 「怎么把本体打包成领域 Skill」 |
| 2.9–2.10 AGENT 构建与工作台 | 「Agent 怎么绑定 Skill 并发布」 |

> 手册是**参考资料**，与插件语义层的对应关系：对象类型 ↔ 业务对象、关系类型 ↔ 对象关系、接口 ↔ 可调用行动（能力封装）、
> 共享属性 ↔ 术语方案、动作类型 ↔ 规则与行动、领域服务 ↔ 服务封装、数据管道 ↔ 对象实例、发布本体 ↔ 本体版本与语义层准出。

## 八、服务封装：本体对外提供能力

按**对象 / 关系 / 规则 / 行动**四类封装：

- **通用 MCP 协议** —— 产出 MCP 工具定义，可直接挂进 DSH 或任何 MCP 客户端（对象封装 = 一个「按条件查对象」的工具）。
- **专有本体 SDK** —— 产出 TypeScript 片段，把语义层做成业务方直接 `import` 的领域模型。

选哪种：要给智能体用 → MCP；要给业务方写代码 → SDK。

---

## 九、把你的开发流程接进来

插件不替你建仓库，它管的是**本体 → 应用**这一段的规格与一致性：

1. 在「场景」里写清楚这次要交付什么（背景 / 目标 / 范围 / 不做 / 验收 / 风险）；
2. 拆功能点，每条功能点挂到语义层资产上——**可追溯矩阵**从这里开始；
3. 语义层定稿后生成蓝图，蓝图就是前后端各自的施工图；
4. 用例写在「校验」页，能写成接口调用的就写成接口调用，平台会真跑一遍并回写结果；
5. 失败用例自动开缺陷卡，修好后复跑通过才关；
6. 卡与场景都准出后，签字归档；本体版本与灰度走「本体版本」页。

## 十、自查清单（贴在新项目第一张卡上）

- [ ] 场景六段齐全（背景 / 目标 / 范围 / 不做 / 验收 / 风险）
- [ ] 本体容器已建，资产都有归属（无归属的会落到「默认」本体）
- [ ] 每个对象都有编码和属性（建模建议器无 blocker）
- [ ] 没有悬空关系、没有无表达式规则、没有无目标行动
- [ ] 每条规则都选了表达式语言，且写清了选型理由
- [ ] 写操作声明了前置条件、副作用与幂等性
- [ ] AI 草稿已逐条校准（确认或废弃），废弃的没留坑
- [ ] 应用蓝图已生成且与语义层一致（语义层改过就重新生成）
- [ ] 服务封装选型已定（MCP / SDK）并能跑通一个调用
- [ ] 平台操作手册已入库（至少覆盖本次要用到的操作）
